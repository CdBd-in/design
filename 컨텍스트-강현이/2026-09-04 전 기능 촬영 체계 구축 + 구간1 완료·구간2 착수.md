## 1부 — 체계가 바뀐 이유

### 발견 1. 「기능 사전」의 ●◐○은 교차검증이 아니었다

기능 사전은 출처가 **가이드센터 한 곳**(46문서)이다. 거기 붙은 `●`는 *"두 출처가 일치"*가 아니라 *"가이드센터가 그렇게 썼다"*는 뜻이었다.

**실제 출처는 4개**였고 3개를 안 쓰고 있었다.

| 출처 | 분량 | 성격 |
|---|---|---|
| 가이드센터 | 46문서 | 엔드유저 소개 |
| **`[DS] 3. 페이지 구조`** | 19문서 · 3,923줄 | 화면·인터랙션 규칙 |
| **`[DS] 4. 카드 기능 정의`** | 17문서 | 카드별 옵션 스펙 |
| **`[T]`·`[SV]` 실무 기록** | ~60건 | `사용자 검증` 실측값 |

→ 엔드유저 기능이 **61건이 아니라 약 130건**이었다(온보딩·뷰어 조작·에러 화면·멀티 내보내기·반응형 분기 등 누락).

### 발견 2. `[DS]`는 제품 사양 근거로 쓸 수 없다

디자인 시스템은 **설계 의도**지 **출시된 제품의 기록이 아니다.** 2-2에서 실증됨 — `[DS] 4-1`이 「카카오톡 공유하기」를 아예 모르고 「선택 카드로 이동하기」를 「페이지 이동하기」로 오기.

> 🔑 **[DS] 단독 근거 사용 금지.** 영상 또는 다른 출처와 교차할 것.

### 결론 — 📹 등급 신설

기능 사전 상단에 박음:

> 📹 **영상 실측(최상위·문서보다 우선)** · ● 문서화 · ◐ 진입점만 · ○ 소개만
> **문서와 영상이 다르면 영상이 맞다.**

## 2부 — 판독 방법 (재사용)

**ffmpeg이 이 기기에 없어** 정적 빌드를 `/tmp/ffbin/`에 받아 씀(시스템 미변경).
```bash
curl -sL -o ff.gz "https://github.com/eugeneware/ffmpeg-static/releases/download/b6.0/ffmpeg-darwin-arm64.gz"
gunzip -f ff.gz && mv ff ffmpeg && chmod +x ffmpeg
```

```bash
V="파일.mov"
# ① 컨택트시트 (전체 흐름 파악)
/tmp/ffbin/ffmpeg -y -v error -i "$V" -vf "fps=1/2,scale=1000:-1,tile=3x3" -q:v 3 "/tmp/s_%d.jpg"
# ② 원본 해상도 크롭 (판정 근거)
/tmp/ffbin/ffmpeg -y -v error -ss {초} -i "$V" -frames:v 1 -vf "crop=W:H:X:Y" -q:v 2 /tmp/zoom.jpg
```

**좌표 기준** (영상 3016×1930): 좌 미리보기 ~430–1100 · 중 카드보드 ~1300–2050 · **우 디자인보드 ~2010–2900**

### ⚠️ 영상 원본은 git 동기화 안 됨 (Desktop)
→ **판정 근거 프레임을 반드시 `영상-판독-프레임/구간N/`에 PNG/JPG로 보관.**
A1(2026-09-03)은 이걸 안 해서 지금 원본을 볼 수 없다.

### 구간 마무리 3단계 (필수 — 3회 연속 빠뜨렸던 것)
1. **판정 목록 ↔ 정본 전수 대조** (빠진 항목 검출)
2. **옛 서술 잔존 검사** (모순 검출 — `grep`으로 폐기된 문구 추적)
3. **녹화 목록에서 해소된 항목 종결 처리** (안 하면 다시 찍으러 감)

## 3부 — 🚨 내가 저지른 오류 4건 (같은 실수 방지)

### ① 정본 반영 누락 — 3회 반복
판독 기록(로그)에만 쓰고 **기능 사전·볼트 가이드에 안 옮김.** 로그는 정본이 아니라 다음 세션에 반영이 안 된다.
- 1차: `[SV]` 볼트 통째로 누락(OG·URL 게시 정본이 거기 있었음)
- 2차: 1-3·1-4 판정이 로그에만
- 3차: 내 계정 진입·버튼 모양·미리보기 refresh 등 5건

### ② 제품 사양과 팀 정책을 뭉갬 — 2회
- **`is_menu`**: `[T]`의 *"기본 OFF"*를 **오류로 정정**했는데, 실은 **룩북 팀이 항상 꺼두는 정책**이었다(제품 기본값은 ON). `[SV] CLAUDE.md`에 *"신규 row는 true로 자동 생성"*이라고 이미 적혀 있었음.
- **텍스트 크기 min**: 제품 하한이 1로 밝혀지자 *"Figma 11px → 12 snap"* 규칙을 풀려 했는데, 그건 **가독성 기준의 팀 규칙**일 수 있음.

> 🔑 **영상은 "제품이 어떻게 동작하나"만 말한다. "우리가 어떻게 쓰기로 했나"는 말해주지 않는다.**
> 팀 규칙을 제품 오류로 오인하지 말 것. 애매하면 **사용자에게 물을 것.**

### ③ 관측값을 한계값으로 단정 — 2회 (사용자 지적)
*"크기 1~200"·"줄간격 min 1.0"*으로 썼으나 **사용자가 시험해본 값**일 뿐이었다.

**원인**: 「핸들이 트랙 끝에 닿음」을 한계 근거로 삼았는데, **범위 밖 값을 입력란에 넣으면 핸들이 그냥 끝에 붙는다**(2-1 보충에서 실증 — 200과 300이 둘 다 우측 끝).

> 🔑 **슬라이더 범위 확정 조건** — 입력란을 쓰지 말고 **슬라이더만 드래그**해서 더 이상 값이 안 변하는 지점. 입력란 허용 범위는 **별개로** 기록.

### ④ 촬영 지시가 한계를 못 잡는 구조였음
*"0 → 4까지 천천히"*처럼 **내가 범위를 미리 적어놓고** 그 안에서만 찍어달라 했다. 사장님은 지시대로 하셨는데 지시가 틀렸다.
→ 지시서 공통 규칙에 **「슬라이더 한계 확인」** 항목 추가함. **구간 3~10의 슬라이더 항목도 순차 수정 필요.**
